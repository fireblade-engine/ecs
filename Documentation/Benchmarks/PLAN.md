## Scope and rules

- Use [`abeimler/ecs_benchmark`](https://github.com/abeimler/ecs_benchmark) only as workload inspiration. Do not add it as a dependency, run a direct Flecs comparison, or claim framework parity from workload names alone.
- Base the suite on upstream logical workloads, not byte-for-byte implementation identity. Port a workload when the revision's APIs can express its intent; document operation, representation, and timing differences. If a native operation is unavailable, classify that native operation as unsupported, or identify any different API-based adaptation explicitly as a semantic difference—never describe an emulation as the unsupported native operation or claim timing equivalence without evidence.
- Keep existing unrelated iteration and storage benchmarks. This work replaces the incomplete Git-ref comparison path, not the whole benchmark package.
- Compare only committed tags, branches, or commit IDs. Resolve every requested ref to a full SHA before starting. Never include uncommitted source or a special `WORKTREE` input.

## Verified starting point

- `Benchmarks/Package.swift` is already a separate Swift Benchmark package and resolves `https://github.com/ordo-one/benchmark` to **1.38.1** in `Benchmarks/Package.resolved`.
- The local `1.4.3` tag declares `Component: AnyObject, Sendable`; the checked-out current revision declares `Component: Sendable` and exposes `Nexus.StorageKind.archetype` and `.sparseSet`. Results must identify component model and backend; those differences are not evidence of equivalent storage behavior.
- Existing reference-derived cases are in `Benchmarks/Benchmarks/ECSBenchmark/ComparisonBenchmarks.swift`, `ReferenceIterationBenchmarks.swift`, and `ReferenceUpdateBenchmarks.swift`. The latter two provide useful starting fixtures for two-system uniform/mixed updates and one-, two-, and mixed-three-component iteration. `OneDimensionBenchmarks.swift` and `StorageBenchmarks.swift` also contain existing, non-reference workloads to preserve.
- The preliminary runner is incomplete: `Scripts/benchmark-compare.sh` copies `Benchmarks/ComparisonHarness/Package.swift`, but that file is absent. The script accepts a baseline/candidate pair and a special `WORKTREE` candidate; it runs repeated benchmark processes per side (three by default), while its JMH parser in `Scripts/benchmark-compare-lib.sh` retains only wall-clock p50. `Scripts/generate-benchmark-report.sh` invokes that runner, rather than consuming N saved result files. `Tests/benchmark-compare-tests.sh` also assumes the missing package manifest exists.
- `Benchmarks/README.md` documents existing semantic differences: `AddComponent` removes the entire batch before timing; the current three-component lookup population/count matches the upstream helper (N created, `ceil(N/2)` looked up), but its `DataComponent` layout and value-copy access differ. In `ComparisonBenchmarks.swift:45,59,81,131`, creation, destruction, and add use `scalingFactor: .one`; `Benchmark.swift:154` defines that as one scaled pass. The benchmark executor calls the closure anew for each warmup and measured iteration (`BenchmarkExecutor.swift:75–78,494–497`), so each invocation gets a fresh Nexus: creation does not accumulate across invocations, destruction does not revisit dead handles, and add does not re-add already-added components. Create/destroy teardown is excluded; AddComponent removes the whole batch before its single timed add pass. `Update7SystemsOnly` uses a different local population and is not proof of parity with either reference update workload.
- Large existing scales reach millions of entities. Use a targeted low-count smoke selection before any full run.
- `Documentation/Benchmarks/REPORT.md` is a bogus remnant: it was hand-written in `c7c83d88`, not produced by any committed tool, and its numbers are not measurements. Do not cite it. It stays in place only until Step 12, where it is replaced by a report generated from real saved results.

### Reference and Fireblade workload matrix

The following IDs are **recommended future result identities**, not current benchmark names. Each is unique even where a parameterized case includes zero (for example, `CreateNoEntities` is not merged with `CreateEmptyEntities / 0`). Reference defaults use `CreateRange(0, 2,097,152, 2)`; `EmitAndUpdateEventsViaObserverWithMixedEntities` alone uses the small range ending at 32,768. The benchmark counters expose entity/component counts, but the C++ registrations do not explicitly divide elapsed time by entities or matches: one reported iteration is a batch/pass. Keep entity count, lookup count, matched count, and per-invocation time distinct. Access behavior is wrapper-specific: in EnTT's generic [`EntityBenchmark.h`](https://github.com/abeimler/ecs_benchmark/blob/98678f746e0e2f04c37a3332453c8d98daa94f92/benchmark/benchmarks/EntityBenchmark.h), getter results are assigned to `auto` locals; its [`EntityFactory.h`](https://github.com/abeimler/ecs_benchmark/blob/98678f746e0e2f04c37a3332453c8d98daa94f92/src/entt/entt/entities/EntityFactory.h) returns references for component one/two, so successful gets copy into locals, while optional component three returns a pointer and a miss copies no component payload. Do not generalize this EnTT behavior to other reference wrappers.

`applicable` means the revision's public APIs can express the registered workload's logical intent; it does not claim a native bulk/pool-wide primitive, an implemented adapter, or equivalent timing. Where expressing the intent requires different operations, the matrix names that semantic/timing difference; a native operation that is absent remains explicitly unsupported. Current-revision applicability includes both `.archetype` and `.sparseSet`; 1.4.3 has no selectable `StorageKind`. The preceding column describes actual local implementations and known differences. No cross-revision adapter has been compiled or benchmarked.

### Compatibility evidence and remaining verification

- Event APIs differ by ref. [`1.4.3 NexusEvent.swift`](https://github.com/fireblade-engine/ecs/blob/1.4.3/Sources/FirebladeECS/NexusEvent.swift) declares structural events only, and [`1.4.3 NexusEventDelegate.swift`](https://github.com/fireblade-engine/ecs/blob/1.4.3/Sources/FirebladeECS/NexusEventDelegate.swift) exposes a Nexus callback. Current [`NexusEvent.swift`](https://github.com/fireblade-engine/ecs/blob/ed692003ec0b268cbed0b823141cc5f382ef790a/Sources/FirebladeECS/NexusEvent.swift) retains structural events and adds `ComponentReplaced`, `ComponentModified`, and `ComponentsModified`; current [`NexusEventDelegate.swift`](https://github.com/fireblade-engine/ecs/blob/ed692003ec0b268cbed0b823141cc5f382ef790a/Sources/FirebladeECS/NexusEventDelegate.swift) and [`NexusEventMask.swift`](https://github.com/fireblade-engine/ecs/blob/ed692003ec0b268cbed0b823141cc5f382ef790a/Sources/FirebladeECS/NexusEventMask.swift) make value-change notifications opt-in. The open `NexusEvent` marker and delegate callback do not themselves expose arbitrary-event dispatch, a queue/drain API, or query-bound user observers; do not treat them as direct ports of those benchmark contracts.
- In both Fireblade revisions, empty/minimal entity creation, destruction, component get/set/remove, and family iteration are expressible. This does **not** prove benchmark parity. Fireblade's `createEntities(count:)` helper loops over ordinary entity creation; it is not the reference's native bulk factory call. The matrix classifies logical API applicability and documents known reference differences; it does not claim cross-version execution or timing parity. Both refs lack native type-wide component clear, so per-entity marker removal is an intentional semantic/timing adaptation.
- `1.4.3` declares `Component: AnyObject, Sendable`; current declares `Component: Sendable` and documents value components. Current exposes `.archetype` and `.sparseSet`; the inspected `1.4.3` source has no corresponding `StorageKind` selection, so do not claim a two-backend `1.4.3` matrix or infer its physical backend name. The current `Reference*` benchmark package has no adapter and is not yet runnable against `1.4.3`; adapter/build feasibility remains for a later approved step.
- `ComparisonBenchmarks.swift` uses both current backends, but creation/destruction timing excludes Nexus teardown; `AddComponent` removes the whole batch before timing; its three-component population/lookup count matches the upstream half-components helper but uses a simplified `DataComponent` and value-returning gets. `ReferenceIterationBenchmarks.swift` matches the mixed helper's membership recipe but currently performs a full family pass without per-entity normalization. `ReferenceUpdateBenchmarks.swift` uses two explicit systems and a persistent world; neither it nor `Update7SystemsOnly` establishes parity with the reference application update registrations.
- Existing tests: [`ReferenceIterationTests.swift`](../../Benchmarks/Tests/ReferenceUpdateTests/ReferenceIterationTests.swift) covers 0/1/small/mixed populations, 512-entity membership, values, and runnable iteration operations on both current backends. [`ReferenceUpdateTests.swift`](../../Benchmarks/Tests/ReferenceUpdateTests/ReferenceUpdateTests.swift) covers 0/1/16/64/128 membership fixtures, system effects, and repeated state changes on both current backends. There is no workload-identity uniqueness test, cross-version adapter test, benchmark reset test, or event/bulk workload test yet.
- **Later focused expectations (not tests added or run in this inventory step):** assert unique stable IDs independently of display names and parameter values; retain distinct `CreateNoEntities` and `CreateEmptyEntities / 0`; assert empty, odd, even, and 99/100 boundary counts; assert created, looked-up, matched, and visited counts separately (including `ceil(N/2)` for unpack-three); assert remove/add returns to starting occupancy; evaluate whether per-entity untimed removal can be measured as one batch, otherwise document the chosen timing boundary; assert mixed iteration family counts and component values; explicitly test update/warmup persistence and event queue drain/reset behavior; and test the component-model/backend availability matrix without claiming unsupported combinations.

The matrix classifies logical workload applicability for both refs using inspected APIs; it does not establish cross-version benchmark execution or exact timing parity. Native bulk, dispatcher, and custom-observer operations are unsupported. The component-event adaptations are applicable with the documented per-entity-clear difference. Validate adapters, matching work and timing in subsequent steps.

## Proposed workflow

1. **One shared suite, thin adapters.** Keep benchmark definitions and configuration shared across refs. Add only the small adapter surface needed for the 1.x reference-component API versus current value-component API, and for available storage backends. Run the same workload definitions and configuration for each ref. Do not encode unsupported operations as no-op substitutes.
2. **Committed-ref runner.** Accept an arbitrary list, for example `--refs 1a1,2b2,3c3`. Resolve all names to full SHAs once; reject invalid inputs before running. Build each ref from an isolated snapshot of its committed tree and use the same committed suite/configuration for every snapshot. Do not copy or overlay uncommitted source. Record the requested ref and resolved SHA separately. No default/current ref should be silently added.
3. **Consistent measurements.** Use the same release configuration, enabled metric set, iteration/scaling policy, setup and timing boundaries, and smoke/full selection for every ref. Preserve meaningful work with the package's black-hole mechanism and correctness assertions. Record whether setup/teardown is measured; do not change it to fit one version. A smoke run selects a small workload/count subset without changing workload semantics. Full-scale execution follows a successful smoke and explicit approval.
4. **One self-contained JSON result per ref.** Store all available statistics for every enabled metric without rounding or reducing the result to p50. Include requested ref, full SHA, run identity/time, suite/workload identity and configuration/hash, Fireblade component model and backend/capabilities, benchmark package version, Swift toolchain, build mode, host/OS/hardware, metric names, units, and parity/availability notes. Keep each file independently interpretable; do not require a sidecar or a later benchmark run to understand it.
5. **Pinned native-baseline export direction.** Store the package's native `BenchmarkResult`/`Statistics` Codable payload in the baseline representation, with writer and reader tied to the Benchmark 1.38.1 and hdrhistogram-swift 0.2.0 pins recorded in `Benchmarks/Package.resolved`; preserve package-provided statistical precision (exact pre-quantization raw samples are not required). This direction is approved, but the internal format is unstable, pins are not a compatibility guarantee, and migration compatibility is unproven. Step 2's scoped probe covers one workload, four metrics, and synthetic cases—not every future suite metric or the complete production pipeline. During Step 8 implementation, add durable round-trip coverage for every enabled metric and the complete wrapper/provenance; require it before Step 8 acceptance, and reject format/version mismatches clearly. Perform real-reference result checks only after the Step 9 runner exists, during the approved Step 12 validation. This approval selects the serialization foundation, not the final app-owned JSON schema or its implementation; define and review that separately in Step 8. Do not silently fall back to p50-only JMH parsing. The existing review gate before the shared suite remains in force.
6. **Independent N-way report generator.** Read N existing result JSON files only; never launch the runner. Match results by stable workload identity, statistic, metric, and compatible unit. Compare and display every available comparable statistic, with explicit units and provenance. Convert units only where their dimensions are known compatible. Missing workloads/fields, unsupported backends, and incompatible units are `unavailable`, never zero or fabricated parity. Guard zero baselines: show absolute values/deltas where valid and mark ratios/percent changes unavailable. Render a Markdown table and Mermaid chart for each comparable numeric statistic/series; keep source JSON unchanged. The existing `Documentation/Benchmarks/REPORT.md` can remain the publication target only with validated output and an explicit overwrite guard.

### Step 10 design (decided under delegation)

- `ECSBenchmarkResults report <result.json>... [--baseline <requested-ref>] [--title TEXT] --output <file.md>`; at least two inputs. The baseline defaults to the first input. Inputs are read-only, and the command never starts a process.
- **Series:** one series per ref × backend, labelled `<requested-ref> (<model>, <backend>)`. A series is compared with the baseline series of the same backend if one exists, otherwise with the baseline's only backend (for `1.4.3`, `default`); the report states each pairing.
- **Matching** by workload identity, scale, and metric. Statistics: measurement count, mean, standard deviation, and the package's default percentiles (p0, p25, p50, p75, p90, p99, p100), read from native `Statistics` without mutating it.
- **Units:** each metric/statistic row is converted to one unit across series only when the dimensions are compatible (time scales, count scales). Anything else, and any missing workload, metric, or backend, prints `unavailable`, never zero.
- **Deltas:** absolute difference plus ratio and percent change; ratio and percent are `unavailable` when the baseline value is zero. Polarity (`prefersLarger`) decides better or worse.
- **Layout:**
  1. Header with title, selection filter, and a provenance table per ref (SHA, suite SHA, configuration hash, component model, backends, toolchain, host, package pins).
  2. A configuration-hash mismatch warning if hashes differ.
  3. Parity notes per workload, and the unsupported list.
  4. For each identity, scale, and metric: a Markdown table (rows are statistics, columns are series with deltas) and one Mermaid `xychart-beta` bar chart with p50 per series.
- Output is deterministic (sorted keys and stable number formatting) and keeps the package's precision.

## Ordered micro-commit roadmap

The titles below are proposed imperative commit messages, not authorization to implement. Each implementation commit must be independently reviewable, bisectable, and revertable; keep the benchmark package buildable and do not break existing entry points between commits. The current comparison path is already nonworking because its expected `Benchmarks/ComparisonHarness/Package.swift` is absent; treat that as a known baseline defect, not a passing check or a regression caused by this work.

### Phase A — settle scope and measurement feasibility

1. **Inventory reference workloads and compatibility**
   - **Scope:** Reconcile every concrete registration at the pinned reference revision—including the entity-suite source discrepancy, conditional event/publish/update registrations, and extended cases—with the partial package workloads. Record stable identities, setup population, operation and match counts, timed boundaries, reset/warmup behavior, normalization, component model, and backend availability; classify logical API applicability for both refs and document known semantic/timing differences and unsupported native operations. Preserve unrelated iteration/storage cases. Do not call an event or extended case unsupported until the registrations and Fireblade API have been checked.
   - **Depends on:** Nothing.
   - **Focused evidence:** A registration-to-identity reconciliation with no unexplained registered cases and inspected API evidence for applicability/unsupported classifications. Document the three-component lookup, add-component timing boundary, and iteration membership/normalization differences; leave two-/seven-system parity explicitly unverified rather than inheriting names as proof.
   - **Review gate:** User reviews the inventory and API-applicability/known-difference classifications before suite changes begin.

2. **Verify lossless benchmark statistics export — scoped probe complete; production coverage pending**
   - **Scope:** Establish whether the package's native result/statistics representation can round-trip at package-provided precision. The scoped probe confirms this for one measured workload across four metrics and synthetic native results. It does not prove every suite metric, the future wrapper/provenance, all possible inputs, format stability, or a complete production pipeline. Exact pre-quantization raw samples are not required.
   - **Depends on:** Step 1's workload/metric inventory.
   - **Approved direction:** Use native `BenchmarkResult`/`Statistics` Codable storage in the package's baseline representation, with writer and reader fixed to the resolved Benchmark 1.38.1 (`ca4a9d300fc15d38132853c2e30462337b33c43f`) and hdrhistogram-swift 0.2.0 (`c2e1210df04b4fff47e53f2f9dad9cc45ae15d63`) revisions recorded in [Package.resolved](../../Benchmarks/Package.resolved). The user accepts format-instability risk ([package stability guidance](https://github.com/ordo-one/benchmark/blob/ca4a9d300fc15d38132853c2e30462337b33c43f/README.md#api-and-file-format-stability)). These pins identify versions, not a stability guarantee; migration compatibility remains unproven. This approves the serialization foundation only, not a complete JSON schema or its implementation.
   - **Probe performed:** An official targeted `TraitMatching` baseline named `opencode-native-roundtrip-20261029-dc3fecf4` was produced for `wallClock`, `cpuTotal`, `throughput`, and `peakMemoryResident`, with 86 measurements per metric. The original baseline-update command transcript is unavailable and is intentionally not reconstructed here. The official `swift package benchmark baseline read opencode-native-roundtrip-20261029-dc3fecf4` successfully decoded and displayed all four metrics.
   - **Round-trip evidence:** A temporary test ran as `cd Benchmarks && swift test --filter ReferenceUpdateTests.nativeBaselineRoundTripPreservesAllFieldsAndStatistics` and passed one test after a located compile diagnostic was fixed. For the saved baseline, native `BenchmarkResult`/`Statistics` types were embedded in a test-local Codable mirror of the plugin-internal baseline envelope, decoded, and re-encoded. A structural canonical comparison of the entire actual saved JSON (normalizing dictionary key order) covered metadata, histogram, and caches. Decoded/re-encoded comparisons covered selected metric, unit and scaling accessors; mean, standard deviation, minimum, maximum, buckets and measurement count; all seven default percentiles; every integer percentile from 0 through 100; selected fractional percentiles; and a cache-mutation sequence. Synthetic in-memory native-result encode/decode cases additionally compared non-default units, scaling, thresholds, tags, zero-only measurements, both `prefersLarger` settings, histogram data, and derived statistics. The real plugin baseline reader was exercised separately by the official read command.
   - **Limits and cleanup:** The plugin's pre-write in-memory result was not accessible, so it was not compared with the saved baseline; the mirror test does not prove the complete production writer/reader pipeline. Round-trip statistic values were checked for equality, not independently validated mathematically. The pinned [`Statistics` initializer](https://github.com/ordo-one/benchmark/blob/ca4a9d300fc15d38132853c2e30462337b33c43f/Sources/Benchmark/Statistics.swift) defaults to three significant digits, so package data may already be quantized; the approved requirement is package-provided precision, not raw pre-quantization inputs. The temporary test was disposable, not a permanent regression test; its code, manifest edits, and unique generated baseline were cleaned after the probe.
   - **Source-observed cache risk:** In the pinned `Statistics` source, default percentiles and automatic units share `_cachedPercentilesHistogramCount`. If measurements are added after default percentiles are cached, a subsequent `units()` call can advance that marker without refreshing the cached percentiles, making stale values appear current. This is a source observation, not a reproduced failure. Avoid mutating completed statistics; if a future production path mutates them, add a focused test for this boundary.
   - **Remaining production requirements:** During Step 8 implementation, add durable round-trip coverage for every enabled metric and the complete app-owned wrapper/provenance, require those tests before Step 8 acceptance, and fail clearly on format/version mismatches. Validate real-reference results only after the Step 9 runner exists, during the approved Step 12 smoke. Keep the existing review checkpoint after Steps 1–2: this plan update does not authorize moving to the shared suite.
